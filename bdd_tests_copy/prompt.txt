**Objective**:
Review and refactor the attached code (in the provided PDF screenshots) to implement a **robust**, **modular**, and **scalable** step definition strategy for automating test cases, based on the defined conversation flow and conditions below.

### 📋 Execution Flow Logic

The expected behavior of the system is defined as follows:

1. **Initial Request** → Response: `expected_complaint_date`
2. **Answer to `complaint_date`** → Response: `expected_complaint_method`
3. **Answer to `complaint_method`** → Response could be:

   * `expected_full_name` → Answer leads to `expected_account_number_selection`
   * or directly → `expected_account_number_selection`
4. **Answer to `account_number_selection`**:

   * **Complaint not related to account number** → `expected_complaint_elaboration`
   * **Account Number not shown** → `expected_add_account_number`
   * **Application Number** → `expected_add_application_number` → then `expected_complaint_elaboration`
   * **Reference Number** → `expected_add_reference_number` → then `expected_complaint_elaboration`
   * **Direct Account Number value** → `expected_complaint_elaboration`
5. **Answer to `complaint_elaboration`** → `expected_follow_up_question1`
6. **Answer to `follow_up_question1`** → `expected_follow_up_question2`
7. **Answer to `follow_up_question2`** → `expected_clarification_revise_action`
8. **Answer to `clarification_revise_action`** → Response could be:

   * `expected_unauthorised_account_handling` → Answer → `expected_contact_willingness_response`
   * or directly → `expected_contact_willingness_response`
9. **Answer to `expected_contact_willingness_response`**:

   * If response is `add_new_phone_email` → `expected_add_new_phone_email`
   * If response is `phone` → `expected_final_summary` → Final response: `expected_complaint_submission`
   * If not any of the above → `expected_final_summary` → Final response: `expected_complaint_submission`

---

### ❗️Current Implementation Issues

1. **Hardcoded or Inflexible Mappings**
   Request–Response pairs are not abstracted, making it difficult to manage and extend.

2. **Lack of Conditional Flow Handling**
   Steps not applicable to certain test cases are still being executed or validated unnecessarily.

3. **Missing Metadata Capture**

   * `conversationID` and `interactionID (Reference Number)` must be captured after each test case.
   * If a test case ends **before** reaching `expected_complaint_submission`, only capture `conversationID`.

4. **Post-Test DB Validation**
   After all test cases are executed and IDs are captured, perform relevant **database validations**.

---

### ✅ Goals for Code Review & Refactor

1. **Improve Step Definitions**

   * Use a dynamic and centralized way to handle the request-response flow.
   * Support skipping of irrelevant steps gracefully based on test data.

2. **Enhance Test Case Flexibility**

   * Ensure that if specific data is missing in the test case, the corresponding steps and validations are automatically bypassed.

3. **Add Metadata Tracking**

   * Capture `conversationID` and `interactionID` at appropriate checkpoints.
   * Ensure fallback handling if full submission flow is not reached.

4. **Integrate Post-Test Validations**

   * Once all test cases are complete, use the captured IDs to trigger backend/database validations.
